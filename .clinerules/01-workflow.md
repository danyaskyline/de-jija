# Правила работы над проектом de-jija

## Контекст — читать в начале КАЖДОЙ задачи

Перед началом любой задачи прочитай:
- docs/game-design.md
- docs/architecture.md
- docs/conventions.md
- docs/decisions.md

Это обязательно, даже если задача кажется маленькой и не связанной с дизайном/архитектурой напрямую.

## Автор проекта не программист

- Объясняй технические термины кратко и просто, если они не были ранее явно введены в docs/.
- Не полагайся на то, что автор прочитает и оценит код построчно — вместо этого после выполнения задачи показывай понятное подтверждение результата (вывод команд, тестов, проверок), а не просто "готово".

## Git-дисциплина (дублирует docs/conventions.md — там подробности)

- После завершения согласованной задачи — коммит с понятным сообщением (Conventional Commits: feat/fix/chore/docs).
- Пушить в origin/main после коммита, если не сказано иное явно.
- НИКОГДА не использовать git push --force или --force-with-lease без явного разрешения ИМЕННО в текущей задаче. Разрешение из прошлой задачи не переносится на новую.
- Перед любой операцией, переписывающей уже опубликованную историю (amend после push, rebase, filter-branch) — сначала создать резервную ветку и показать результат ДО push, дождаться подтверждения, и только потом пушить.

## Работа с системными процессами

- Перед завершением ЛЮБОГО системного процесса (kill/stop/taskkill и т.д.) — всегда проверять полную команду запуска (full command line), а не только совпадение по имени процесса или подстроке в пути.
- Причина: подстрока вроде "npm" в пути может совпасть с процессом самого агента или другим важным процессом, а не только с целевым (реальный случай в этом проекте — см. историю задачи walking skeleton).


## Приоритет: объяснять, а не молча выполнять

Если инструкция автора противоречит лучшей практике или рискует потерей данных/качества — не выполнять буквально. Сначала объяснить проблему и предложить альтернативу, дождаться решения. Слепое исполнение буквальной команды — не приоритет.

## Данные vs код (ключевой архитектурный принцип, см. docs/conventions.md)

Юниты, предметы, способности, рецепты крафта — это данные (JSON/таблицы БД), не классы и не захардкоженные условия в коде. Любое дублирование значений вместо ссылки по id — ошибка, которую нужно исправлять сразу, а не откладывать.

## Архитектурные решения — фиксировать, не терять

Если в ходе задачи принимается новое значимое архитектурное решение (или меняется/уточняется старое) — предложи автору добавить запись в docs/decisions.md по существующему формату файла, прежде чем считать задачу завершённой.

## Порядок разработки

Идти узкими, проверяемыми шагами (walking skeleton → небольшие приросты). Не реализовывать сразу большую систему целиком за одну задачу, даже если это кажется быстрее.
