# Роль веб-ИИ и как к нему обращаться

## Кто есть кто

- **Автор** — владелец проекта, не программист. Ставит цели, принимает продуктовые решения. Единственный канал связи между CLI-агентом и веб-ИИ.
- **Веб-ИИ** — «мозг»: архитектура, дизайн игровых правил, ревью, разбор тупиков. Код не пишет и репозиторий не видит.
- **CLI-агент** — исполнитель: код, тесты, доки, состояние в репозитории. Работает автономно и сам решает, когда нужен веб-ИИ.

## Чего у веб-ИИ нет (отсюда все правила)

- Нет доступа к репозиторию и к ссылкам: он читает только то, что приложено к чату.
- Нет доступа к чату CLI-агента: всё, что тебе кажется очевидным, ему неизвестно, пока этого нет в пакете.
- Нет памяти между чатами: автор каждый раз открывает новый чат. Репозиторий — память проекта, чат — нет. Любое принятое решение CLI-агент сразу записывает в файл (раздел «Решения» задачи; значимые — ADR в `decisions.md`; старые ADR не переписываются).

## Два разных события: консультация ДО кода и ревью ПОСЛЕ кода

### Триггер 1. Консультация до кода

Шаг требует консультации, если он:
- меняет игровое правило;
- меняет архитектуру или границы модулей;
- меняет формат данных в `/shared`;
- меняет публичный API `Battle`;
- или спецификация неоднозначна и агенту приходится выбирать между вариантами.

Порядок: пакет → ответ в `docs/reviews/` → запись в `decisions.md` → код.

- **Пакет короткий:** спецификация, 2–3 варианта с ценой каждого, рекомендация агента,
  фрагменты документов, которые изменятся. Кода и диффа в нём нет — их ещё не существует.
- **Запрещено начинать реализацию такого шага до ответа.**
- **Тишина — не согласие.** Если ответа нет, агент не реализует «рекомендованный» вариант. Он берёт
  шаги без метки консультации или завершает сессию и сообщает автору, что шаг ждёт ответа.
- **Ответ получен**, только когда автор положил его в `docs/reviews/`, а шаг в плане ссылается на этот файл.
- **При сомнении** («подпадает ли шаг под триггер») — подпадает.
- **Если выяснилось по ходу:** шаг без метки затронул область триггера. Остановиться, поставить метку,
  отправить пакет; написанное не коммитить до ответа.

### Триггер 2. Ревью после кода

Ревью проверяет исполнение, а не замысел. Оно не заменяет консультацию и не отменяет её. Если код был
сделан без требовавшейся консультации, ревьюер фиксирует это как нарушение, возвращает решение на
консультацию, а запись о нём остаётся в «Решениях без консультации» со статусом «не ратифицировано».

### Честный предел

Никакой механизм не докажет, что пакет ушёл до первой строки кода: скрипт видит лишь, что файл ответа
существует и в каком коммите появился. Единственная независимая опора — автор сам копирует ответ в
`docs/reviews/`. Отсутствие этого файла — факт, который агент не может подделать от имени автора.

## Когда обращаться: ОБЯЗАТЕЛЬНО (нельзя решать молча)

1. **Дизайн игровых правил:** новое правило боя, баланс, поведение, которого нет в docs; расхождение docs и кода.
2. **Архитектура:** новая граница модулей, формат данных или протокола, новая зависимость, смена мажорной версии, структура папок, всё, что тянет новую ADR.
3. **Ревью перед закрытием каждой задачи**, и после шага, который задача помечает как «с ревью».
4. **Тупик:** два разных подхода к одной проблеме не сработали; тесты красные без понятной причины; ловишь себя на правке теста под код.
5. **Неоднозначная постановка:** два толкования ведут к разной реализации.
6. **Рост сложности:** файл или функция заметно разрастаются, решение выглядит костылём, который придётся переписывать.

Сомневаешься — обращайся: один лишний вопрос дешевле неверной архитектуры.

## Когда НЕ обращаться

Названия, рефакторинг внутри файла, опечатки, оформление, всё, что прямо описано в docs или задаче, рутинные шаги плана. Решай сам, фиксируй в «Прогресс».

## Правило мышления

Перед обращением ты сам продумываешь вопрос: находишь 2–3 варианта и формулируешь свою рекомендацию. Пакет без собственного анализа недопустим: веб-ИИ проверяет и дополняет твоё решение, а не заменяет мышление.

## Как обращаться: пакет-файл

Ты НЕ просишь автора формулировать вопрос. Собираешь файл в папке автора для пакетов: `~/Desktop/PROMPTStoWebAI/NNN-тема.md` — **вне репозитория**, чтобы пакет случайно не уехал в коммит (NNN — порядковый номер; старые не удаляй). На Windows путь = `Join-Path $HOME 'Desktop\PROMPTStoWebAI'`. Правишь автору: путь к файлу и «приложи его к новому чату с веб-ИИ». Больше от автора ничего не требуется. В пакет не попадают секреты (`.env`, ключи, токены).

Структура пакета, в этом порядке:

1. **Преамбула** (фиксированный текст): «Ты — архитектор и ревьюер проекта de-jija: браузерная MMO в духе HoMM3, монорепо server/client/shared/docs/config. Автор не программист, код пишет CLI-агент. Прочитай файл целиком. Репозиторий закрыт, ссылок не открывай. Не выдумывай код, которого нет в файле; если данных не хватает — запроси их конкретно. Отвечай по формату ОТВЕТ ВЕБ-ИИ».
2. **ВОПРОС ВЕБ-ИИ:** Тип (дизайн / архитектура / ревью / тупик / уточнение); Задача (id, название, шаг); Контекст (3–5 строк: что сделано, что мешает, что пробовал); Вопрос (одно предложение); Варианты (2–3, у каждого плюсы, минусы, цена изменений) и твоя рекомендация с причиной; Что нужно в ответе (решение / замечания / план шагов).
3. **Материалы**, вставленные текстом, каждый с заголовком «Файл: путь, строки X–Y»: часть A START-HERE («Проект в 5 строках» и «Как устроен процесс»); файл активной задачи целиком («Прогресс» и «Решения»); `docs/conventions.md` целиком, если вопрос про архитектуру или правила; затем только нужные куски кода и docs по диапазонам строк, не целые файлы. Для ревью дополнительно: `git diff` коммитов задачи, вывод `npm test` и `npm run check`, что считаешь слабым местом.
4. Лимит: примерно до 800 строк. Не помещается — режь куски кода по диапазонам, но не отбрасывай задачу и conventions. Последняя строка пакета: «Пакет собран на коммите <хэш HEAD>».

## Формат ОТВЕТ ВЕБ-ИИ

Решение (одно предложение); обоснование (коротко); что записать в репозиторий (задача / ADR / docs); следующие шаги; оговорки. Нужны данные — веб-ИИ просит их конкретно, а не угадывает. Автор вставляет ответ CLI-агенту целиком.

## После ответа

1. Запиши решение: «Решения» в файле задачи; архитектурное — новая ADR (старые не переписываются). Сама запись в репозиторий — по [`sync.md`](./sync.md).
2. Ответ расходится с твоей рекомендацией — исполняй ответ веб-ИИ, возражение изложи в следующем пакете.
3. Ответ противоречит conventions или docs — не правь молча ни то, ни другое: сообщи автору.
4. Продолжай работу без «продолжай» от автора.

## Ревью перед закрытием задачи

Не закрывай задачу без ревью веб-ИИ. Пакет для ревью: diff, зелёные `npm test` и `npm run check`, заполненные «Прогресс» и «Итог», обновлённая часть B. Закрывай после ответа веб-ИИ.

- **Числа в пакете — вместе с командой, которой они получены, и с ручной проверкой максимума:** откройте один-два самых «выдающихся» пункта и убедитесь, что число описывает именно их.
