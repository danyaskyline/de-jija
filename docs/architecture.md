# Architecture

## Стек (зафиксировано, см. decisions.md)
- Язык: TypeScript везде (сервер и клиент).
- Сервер: Node.js, HTTP+WebSocket (напр. Express + ws).
- БД: PostgreSQL — персистентность (аккаунты, инвентарь, рынок, кланы, логи). НЕ хранит live-состояние карты.
- Клиент: PixiJS (Canvas/WebGL рендер) как PWA; десктоп-обёртка — Tauri (тонкий webview, легче Electron).
- Мир/карта на сервере: ECS-подход (библиотека bitECS) — обоснованно именно для этого слоя (много однородных тикающих сущностей: игроки, мобы, ресурсы).
- Бой: НЕ полноценный ECS-фреймворк — данные (статы) + список тегов-способностей, простая объектная модель. На масштабе ~14 юнитов на бой выгоды ECS-фреймворка не реализуются, а оверхед есть.

## Сервер — общая модель
Единый процесс держит весь мир в памяти (шардинг не нужен вплоть до ~1000 concurrent). Три слоя состояния:
1. Статический террейн — читается один раз, почти не меняется.
2. Динамическое содержимое клеток (здания/ресурсы/мобы/иконки боя) — меняется по событиям, не по фиксированному тику.
3. Позиции/состояния игроков — самое частое, но лёгкое по вычислениям.

Сервер спроектирован как **событийный (event-driven / scheduler)**, а не тикающий с фиксированной частотой 10-20 Гц — большинство проверок (респавн, таймер боя, пересечение клетки) естественно реализуются как отложенные задачи ("выполнить в момент X"), а не постоянный опрос.

Память: тысячи объектов карты (мобы/ресурсы) — это единицы-десятки МБ в памяти (структуры по ~200-500 байт), не проблема даже на порядок больше реального масштаба. На клетке хранится только идентификатор типа объекта (напр. `mobType: "skeleton_archer"`), не арт — картинки живут только в клиентских ассетах.

## Карта и клетки — два слоя проверок
- **Проходимость для построения маршрута**: стены, здания, ресурсы, мобы, 8 клеток вокруг моба (только в немирной зоне), иконки боя — непроходимы. Враждебные игроки непроходимы друг для друга при построении маршрута; на мирных клетках — нет.
- **Проходимость для фактического движения**: то же + нельзя пройти сквозь враждебную клетку транзитом (но можно проложить путь ДО неё, чтобы атаковать).
- Моб: сама клетка непроходима для входа, но 8 клеток вокруг (в немирной зоне) — проходимы, вход в любую из них триггерит бой. Иконка боя встаёт на клетку моба, а не на клетку, откуда зашёл игрок (сервер логически "довставляет" игрока на клетку моба для целей боя).

## Движение — протокол
- Клик — строит маршрут локально на клиенте (визуально, без сети).
- Повторный клик (подтверждение) — уходит запрос на сервер: `MoveRequest { targetX, targetY }`.
- Сервер авторитетен всегда: пересчитывает путь сам по актуальной карте блокировок.
- Формат ответа — путь целиком с таймкодами, не позиция на каждый тик:
```
MoveStart { entityId, path: [{x,y,t}, ...] }
```
- Прерывание/смена скорости в процессе → пересчитанный остаток пути от текущей фактической точки:
```
MoveInterrupt { entityId, x, y, reason: enum(combat|blocked) }
MoveSpeedChanged { entityId, fromX, fromY, remainingPath: [{x,y,t}, ...] }
```
- Новый наблюдатель, входящий в зону видимости на середине чужого движения — получает снепшот:
```
EntitySnapshot { entityId, currentX, currentY, remainingPath, speed }
```
- Камера на клиенте: центрируется на той же непрерывной интерполированной координате, что и модель героя (`cameraPosition = interpolatedPlayerPosition` каждый кадр). Никакого ручного сдвига камеры — всегда автоцентр, опционально лёгкий lerp/smoothing для инерции.

## Бой — модель "инстанса"
- НЕ тикающий процесс — событийная state machine (как шахматный движок), реагирует на действия игроков. Таймер хода — отдельная отложенная задача (timeout), не общий тик.
- "Инстанс" — просто объект в памяти общего серверного процесса (паттерн actor/state-machine), НЕ отдельный сервер/процесс:
```
Battle {
  battleId, board: Hex[], units: [...],
  turnQueue, currentTurnIndex, turnTimer,
  spectators: [connectionId, ...]
}
```
- Старт боя — атомарное сообщение (не два последовательных, чтобы не было рассинхрона кадров: модель+иконка меняются одновременно):
```
BattleStart { battleId, x, y, removeEntityIds: [...], spawnIcon: {x,y,battleId} }
```
- При старте сервер один раз подгружает из БД данные армии/предметов игрока(ов) в объект Battle; во время боя работает только с памятью; по окончании — один раз пишет результат обратно в БД.
- Конец боя: победитель возвращается на клетку боя; проигравший в PvP — телепортируется в город (прямая смена координат, не пошаговое движение).
- Зритель (3-й игрок) — read-only подписка на состояние конкретного battleId, без права действий.

## Спавн мобов и ресурсов
- Точка спавна хранит: тип, таймер респавна, состояние (жив/мёртв, доступен/истощён).
- Спавн моба и последующий (опциональный) старт боя — два разных, последовательных события, не одна операция.
- Группа мобов (переменное число) — одно сообщение со списком:
```
MobGroupSpawn { mobs: [{entityId, mobType, x, y}, ...] }
```
- Наблюдателям для отрисовки не нужны полные боевые статы моба, только тип/уровень — полные статы подгружаются только участникам боя.
- Ресурсы — та же логика таймера, без боевой составляющей; блокируют маршрут как обычный объект.

## Область видимости (AOI)
- Не подстраивается под форму экрана клиента — квадратные чанки с запасом (напр. 32×32 клетки), клиент сам обрезает лишнее под свой вьюпорт (frustum culling, локально).
- Игрок подписан на 3×3 чанка вокруг своего. Размер чанка должен быть заведомо больше максимальной дальности видимости на экране.
- Гистерезис на границах: подписка сразу при пересечении границы, отписка — только после отхода вглубь на несколько клеток (без дребезга).

## Модель данных (основные сущности)
- **Account** — id, логин, email, хэш пароля, статус.
- **Character/Hero** — id, account_id, раса, координаты, текущий город (точка возврата).
- **SkillTree** — character_id → список открытых узлов (эффекты — данные, не код).
- **UnitTemplate** — id, название, раса, тип, базовые статы, список ссылок на AbilityTag, кривая стоимости харизмы. Единственный источник правды по юниту — все системы читают по id, не копируют значения.
- **AbilityTag** — справочник способностей (NoRetaliation, AreaAttack, MagicImmune, Piercing(N) и т.д.) + обработчик в боевом движке.
- **ArmySlots** — character_id → 7 слотов (unit_type_id, текущее/макс. количество, таймер восстановления). Макс. харизма — вычисляется на лету из прокачки+тира, не хранится напрямую.
- **ItemTemplate** — id, слот экипировки, тир, базовые бонусы, теги спецэффектов.
- **ItemInstance** — ссылка на ItemTemplate + владелец/место на рынке + состояние (прочность, надет ли). Сами игровые эффекты не дублируются в инстансе.
- **Inventory** — character_id → список ItemInstance на складе в городе (это остаётся после full loot).
- **CraftingRecipe** — выходной ItemTemplate+тир, требуемые ресурсы, требуемое здание.
- **Market** — листинги (item_instance_id, продавец, цена), агрегированная история сделок по (шаблон+тир).
- **Clan / War** — clan_id, список участников; отдельно флаг активной войны между двумя clan_id.

## Формулы урона
Изолированная чистая функция, не размазанная по боевому движку (`server/src/combat/resolveAttack.ts`):
```
resolveAttack(attacker: CombatUnit, defender: CombatUnit, context: AttackContext, rules?: CombatRules)
  → { damageDealt, defenderHpAfter, retaliationTriggered, blockedByImmunity, breakdown, notes }
```
`rules` по умолчанию — коэффициенты баланса, загруженные в память при старте сервера; `context.random` инжектится, поэтому тесты полностью детерминированы.

Фиксированный порядок шагов (теги атакующего → теги защитника → расчёт по статам → модификаторы → применение):
1. **Теги атакующего** — тип атаки: `MagicDamage` на атакующем = магическая, иначе физическая.
2. **Теги защитника** — `MagicImmune` даёт ПОЛНЫЙ блок входящей магии (это не то же самое, что частичный `magicResistPercent`).
3. **Бросок урона стека** — `roll(damageMin × stackCount .. damageMax × stackCount)`, `stackCount` по умолчанию 1.
4. **Flat-бонус** — `flatDamageBonus` в единицах урона, применяется ДО множителя атака/защита.
5. **Множитель атака/защита** — по коэффициентам из `config/combat-rules.json`:
   - `attack > defense`: `min(attackAdvantageCapPercent/100, 1 + attackAdvantagePercentPerPoint/100 × (attack − defense))`;
   - `attack < defense`: `max(defensePenaltyFloorPercent/100, 1 − defensePenaltyPercentPerPoint/100 × (defense − attack))`;
   - равны: `1`.
6. **Процент-бонус** — `percentDamageBonus`, применяется ПОСЛЕ множителя: `× (1 + percentDamageBonus/100)`.
7. **Магическое сопротивление** — `magicResistPercent` снижает урон магической атаки на этот процент (только для магических атак, значение приводится к диапазону 0..100); это частичное снижение, а не блок.
8. **Мораль** — при `isMoralePenalized = true` итог умножается на `moralePenaltyMultiplier`.
9. **Минимум урона** — итог округляется вниз и не может быть меньше `minimumDamage` (тоже из конфига).
10. **Ответка** — возможна, если у атакующего нет `NoRetaliation`, защитник жив после удара и текущий удар не является ответкой на ответку (`isRetaliation`).

Конфигурация баланса — файл, НЕ БД. Все коэффициенты формулы лежат в `config/combat-rules.json` (`attackAdvantagePercentPerPoint`, `attackAdvantageCapPercent`, `defensePenaltyPercentPerPoint`, `defensePenaltyFloorPercent`, `magicResistIsPercentReduction`, `moralePenaltyMultiplier`, `minimumDamage`), читаются ОДИН раз при старте сервера в память (`server/src/combat/combatRules.ts`) и передаются в `resolveAttack`; сам `resolveAttack` файл никогда не читает. Битый или неполный файл валит старт с понятным сообщением (например «отсутствует обязательное поле minimumDamage»). Файл правится руками и версионируется git — см. decisions.md, 012.

Отложено осознанно (явные заглушки в `AttackContext`, всегда 0): `meleeOffenseBonusPercent`, `rangedOffenseBonusPercent`, `magicOffenseBonusPercent` (боевые мастерства героя) и `defensiveArmorReductionPercent` (снижение ТОЛЬКО физического урона — контакт и стрелки, никогда магия). Источник (дерево специализаций / предметы / что-то ещё) — открытый вопрос дизайна, текущий этап он не блокирует. Пока логики нет: ненулевое значение заглушки не влияет на расчёт, но попадает в `notes`, чтобы заглушку нельзя было принять за работающий бонус. Также не реализованы `AreaAttack` (нужны позиции на гекс-поле) и `Piercing`.

Отладка: результат содержит `breakdown` — каждое промежуточное значение (`stackRoll`, `flatBonusApplied`, `afterFlatBonus`, `attackDefenseMultiplier`, `afterAttackDefense`, `percentBonusApplied`, `afterPercentBonus`, `magicResistApplied`, `afterMagicResist`, `moraleApplied`, `finalDamage`) плюс `notes`. Ручная проверка — песочница боя (см. следующий раздел). Формула обязана быть покрыта юнит-тестами на конкретных парах юнитов (это единственный практичный способ проверить все хитрые комбинации иммунитетов и особых свойств).

## Отладочный инструмент: песочница боя (временный)
- `GET /debug/combat-sandbox` — HTML-форма для ручной проверки (`server/debug/combat-sandbox.html`). Не часть игрового клиента, не связана с авторизацией персонажа, ничего не сохраняет.
- `POST /debug/attack` — принимает параметры атакующего/защитника и context, возвращает полный результат `resolveAttack` с `breakdown`.
- HTTP выбран вместо WebSocket намеренно: инструмент — это «заполнил форму → получил разбор», а игровой протокол в `/shared` засорять не нужно; endpoint удобно дёргать и через curl.
- Локальный инструмент разработчика: при `NODE_ENV=production` роут не монтируется, модуль помечен `// DEBUG-ONLY, remove before Phase 1` и удаляется вместе с `server/src/debug/` (docs/conventions.md).

## Оценка стоимости сервера (грубый ориентир, РФ-хостинг)
- 50–100 игроков: одна машина (сервер+БД вместе), ~1100–2000 ₽/мес.
- 300 игроков: сервер и БД разнесены, ~5000–7000 ₽/мес.
- 1000 игроков: выделенный сервер + отдельная БД, ~10000–18000 ₽/мес.
Оценка по архитектуре, не по нагрузочному тесту — проверяется эмпирически перед реальным масштабированием.

## Хостинг/деплой на старте
- Cloudflare Tunnel НЕ использовать — с 2024 г. под растущими ограничениями Роскомнадзора, нестабилен для тестировщиков из РФ.
- itch.io не обязателен — свой Node.js-сервер может сам отдавать статику клиента (`express.static`) и WebSocket с одного адреса.
- На старте тестирования — локальный запуск + временный туннель (ngrok) ИЛИ сразу дешёвый VPS в РФ (проще и стабильнее для тестировщиков).
