# Conventions — правила проекта

Эти правила обязательны для любого ИИ-агента, работающего над проектом — в любом инструменте. Перед началом задачи — свериться с этим файлом.

## С чего начинать
- **Первым делом прочитать [START-HERE.md](https://github.com/danyaskyline/de-jija/blob/main/START-HERE.md)** — короткая входная страница: постоянные правила (часть A) + текущее состояние (часть B). Не начинать сессию с обхода репозитория.
- Проект ведётся по задачам в [`docs/tasks/`](./tasks). Активная задача — в части B `START-HERE.md` и в README, раздел «Статус».
- Затем читать **только нужную задачу** — не весь репозиторий. Карта файлов с полными ссылками: [`docs/INDEX.md`](./INDEX.md) (обновляется командой `npm run map`).
- Прежде чем браться за работу: прочитать раздел **«Прогресс»** в файле активной задачи — там указано, что уже сделано, на каком шаге остановились и какие особенности тестов не стоит переоткрывать.
- Не начинать задачу заново и не переписывать то, что предыдущие шаги уже сделали, не прочитав этот раздел.

## Общее
- Язык всего кода — TypeScript, и на сервере, и на клиенте. Не смешивать с чистым JS без причины.
- Автор проекта не программист — код должен сопровождаться понятными названиями переменных/функций и минимальными комментариями на ключевых местах (особенно в боевой логике), а не "плотным" кодом без пояснений.
- Один язык коммитов и комментариев в коде — русский или английский, выбрать один и придерживаться (рекомендация: английский в коде/комментариях, русский — в /docs).

## Данные vs код (ключевой принцип)
- Юниты, предметы, способности, рецепты крафта — это **данные** (JSON/таблицы БД), НЕ классы/захардкоженные условия в коде.
- Боевой движок и другая логика читают эти данные по id, никогда не копируют/не дублируют значения в нескольких местах.
- Если нужно добавить нового юнита/предмет — это добавление записи данных, не новый код.

## Структура репозитория (ориентир, уточняется по ходу)
```
/server      — игровой сервер (TS, Node.js)
/client      — клиент (TS, PixiJS)
/shared      — общие типы/константы между server и client (напр. описания сообщений протокола)
/docs        — документация проекта (этот файл и соседние)
```

## Сеть и авторитетность
- Сервер всегда авторитетен. Клиент никогда не решает исход действия сам — только визуализирует то, что подтвердил сервер.
- Формат сообщений — JSON на старте разработки (сознательно, ради скорости итерации; переход на бинарный формат возможен позже без переписывания логики).
- Не рассылать полное состояние всем подряд — использовать зону видимости (чанки), а не broadcast всем клиентам.

## Архитектурные границы
- Логика карты (движение, спавн, AOI) и логика боя — разделены. Бой не знает о карте напрямую, получает на вход только состав армии/предметов и отдаёт результат.
- **Игровые правила боя живут только в `Battle` (`server/src/battle/`) и в чистых формулах (`server/src/combat/`). Код песочницы и интерфейса правил не содержит:** он только отправляет команды и показывает присланные события. Если правило пришлось написать в песочнице или в клиенте — оно не на своём месте (docs/battle.md, 019).
- Боевой движок — чистая функция от входных данных (`resolveAttack` и аналоги), без побочных обращений к БД во время самого боя. Данные для боя загружаются один раз при старте инстанса, результат сохраняется один раз в конце.
- Любое изменение `resolveAttack` (формулы урона) обновляет [`combat-formula.md`](./combat-formula.md) в том же коммите. Формула описана в одном месте: порядок шагов, ключи конфига, источник каждого значения, статус и имя покрывающего теста. Если меняется код и не меняется этот файл — коммит неполный.

## Порядок разработки
- Сначала — узкая, проверяемая задача (walking skeleton, потом маленькими шагами), не пытаться реализовать сразу большую систему целиком.
- Временные/дебажные функции (например, "выдать любые предметы бесплатно" на этапе арены) — помечать явно в коде (например, комментарием `// DEBUG-ONLY, remove before Phase 1`) и выносить в отдельные, легко удаляемые модули/эндпоинты, не смешивать с обычной игровой логикой.
- Постоянные инструменты разработчика (например, песочница боя в `server/src/debug/`) — помечать в коде и в документации маркером `// DEV-TOOL: not mounted in production` и не монтировать при `NODE_ENV=production`. Удалять их перед Phase 1 не требуется; зато нельзя забыть этот запрет — роут не должен попасть в production.
- Любое значимое архитектурное решение — сначала фиксируется в `decisions.md`, потом реализуется.

## Не делать (сознательно исключено)
- Не тащить полноценный ECS-фреймворк в боевую логику (см. architecture.md — обоснование).
- Не хранить live-состояние карты в PostgreSQL — только в памяти сервера.
- Не отправлять позицию игрока на каждый тик — только путь с таймкодами при старте движения.
- Не использовать Cloudflare Tunnel для тестирования (нестабилен для пользователей из РФ).

## Git-дисциплина
- После завершения каждой согласованной задачи — делать коммит с понятным сообщением в духе Conventional Commits (feat:, fix:, chore:, docs: и т.д.).
- Пушить в origin/main после коммита, если не сказано иное явно.
- НИКОГДА не использовать `git push --force` или `git push --force-with-lease` без явного отдельного разрешения в конкретной задаче — даже если обычный push уже стал рутиной.
- Не коммитить .env и любые файлы с реальными секретами/ключами (это уже покрыто .gitignore, но проверять при подозрении).
- Wip-коммиты (`wip: ...`) разрешены **только** по триггеру «лимит»/«handoff» (см. [`docs/workflow/handoff.md`](https://raw.githubusercontent.com/danyaskyline/de-jija/main/docs/workflow/handoff.md)) — чтобы передать состояние в другой чат. Во всех остальных случаях — обычные коммиты по Conventional Commits, как описано выше.
