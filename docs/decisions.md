# Decisions — журнал архитектурных решений

Формат записи: дата/порядковый номер, решение, причина. Не переписывать старые записи — при пересмотре добавлять новую запись со ссылкой на предыдущую.

---

## 001 — Базовый стек
**Решение**: TypeScript + Node.js на сервере и клиенте, PostgreSQL как БД, PixiJS для рендера, Tauri для десктоп-обёртки (не Electron).
**Причина**: один язык упрощает работу соло-разработчику без опыта программирования и его ИИ-агентам; TypeScript и PostgreSQL — самые массово представленные в обучающих данных ИИ-моделей стеки, меньше ошибок у агента; Tauri легче и экономичнее Electron при том же результате.

## 002 — Модель мира: данные + событийный сервер
**Решение**: сервер держит весь мир в памяти одного процесса (без шардинга вплоть до ~1000 concurrent), работает событийно (scheduler/отложенные задачи), а не тикает с фиксированной частотой 10-20 Гц.
**Причина**: для клеточной, небыстрой игры (не физика, не шутер) большинство серверных проверок (респавн, таймер боя, пересечение границы клетки) естественно ложатся на "выполнить в момент X", постоянный высокочастотный опрос не нужен и тратит CPU впустую.

## 003 — Движение: путь с таймкодами, не позиция на тик
**Решение**: сервер при старте движения присылает клиентам весь путь целиком со временем прибытия на каждую клетку, а не текущую позицию на каждый сетевой тик.
**Причина**: резко снижает сетевой трафик и число сообщений; клиент интерполирует локально; при смене скорости/прерывании сервер шлёт пересчитанный остаток от текущей фактической точки.

## 004 — Бой: данные+теги, без ECS-фреймворка
**Решение**: юниты описываются как статы + список тегов-способностей (AbilityTag), боевая логика — прямой объектный код с проверкой тегов в фиксированном порядке, не полноценный ECS-движок.
**Причина**: на масштабе ~14 юнитов на бой выигрыш ECS по производительности (cache-friendly итерация по тысячам сущностей) не реализуется, а оверхед на API запросов/архетипов — есть. При этом сама идея переиспользуемых компонентов-тегов (не Ctrl+C/V под каждого юнита) сохраняется и без фреймворка.

## 005 — Карта: ECS-подход (bitECS) оправдан
**Решение**: для слоя карты (движение, видимость, спавн мобов/ресурсов) использовать облегчённую ECS-библиотеку.
**Причина**: здесь реальный сценарий "много однородных сущностей, разные комбинации компонентов, нужна эффективная построчная обработка на каждый цикл" — именно то, под что ECS создавалась.

## 006 — Full loot только на надетый шмот, армия не теряется
**Решение**: при поражении в PvP игрок теряет только надетые предметы. Прокачка, склад, деньги — сохраняются. Армия никогда не переходит победителю и не пропадает — только временно "ужимается" по кулдауну восстановления харизмы/юнитов.
**Причина**: целевая аудитория (фанаты HoMM3, не только Albion) не готова к полной суровости full loot из Albion; связка "шмот теряется → харизма падает → армия временно слабее" даёт значимость поражения без "спирали смерти" до нуля.

## 007 — Хостинг тестирования: не Cloudflare Tunnel
**Решение**: не использовать Cloudflare (включая Tunnel) для тестового доступа из России; на первое время — локальный запуск + временный туннель (ngrok) или сразу недорогой VPS в РФ; сервер сам отдаёт статику клиента, itch.io не обязателен.
**Причина**: Cloudflare с 2024 г. под нарастающими ограничениями Роскомнадзора в РФ, доступ нестабилен для тестировщиков внутри страны.

## 008 — Разработка: Claude (веб) — дизайн/архитектура/ревью, DeepSeek/Cline — реализация
**Решение**: сложные решения сначала прорабатываются словами в веб-чате (Claude или DeepSeek), фиксируются в /docs, затем как готовое ТЗ передаются агенту (Cline+DeepSeek) на реализацию.
**Причина**: у автора нет опыта программирования — контроль качества идёт через письменные правила (conventions.md) и периодическое ревью структуры проекта "умной" моделью, а не через чтение кода лично.

## 009 — Постоянные правила для ИИ-агентов вынесены в .clinerules/
**Решение**: базовые правила работы (обязательное чтение /docs в начале задачи, Git-дисциплина, приоритет объяснения над буквальным исполнением, данные vs код, порядок разработки) живут в `.clinerules/01-workflow.md` и версионируются вместе с кодом.
**Причина**: правила не нужно повторять в каждом промпте, они ревьюятся и меняются как код; при смене агента/сессии контекст подгружается автоматически.

## 010 — Walking skeleton: структура монорепозитория, версии и настройки по умолчанию
**Решение**: один репозиторий = npm workspaces (`/shared`, `/server`, `/client`), один `npm install` в корне; `package.json` в каждой папке, общий `tsconfig.base.json` в корне; типы протокола подключаются как воркспейс-пакет `@de-jija/shared` (только type-only import, без рантайм-кода в общих модулях). Сервер по умолчанию слушает `127.0.0.1:3000` (переопределяется `HOST`/`PORT`), HTTP и WebSocket — на одном порту; если существует `client/dist`, сервер отдаёт его статикой (реализация пункта architecture.md про деплой с одного адреса). Зафиксированы мажорные версии: express 5, ws 8, pixi.js 8, vite 8, typescript 7, tsx 4 — диапазонами `^` в `package.json` плюс `package-lock.json` в репозитории.
**Причина**: одна команда установки и один набор конфигов — минимум поводов для ошибок у автора без опыта программирования; type-only общий пакет не создаёт рантайм-зависимости клиента от серверного кода; `127.0.0.1` по умолчанию не светит dev-сервер в локальную сеть и не вызывает запросов брандмауэра Windows; `package-lock.json` в репозитории даёт воспроизводимую установку (в т.ч. защищает от повторения случая с неполной распаковкой pixi.js).

## 011 — resolveAttack: формула урона, инъекция RNG и форма результата
**Решение**: урон = `max(MIN_DAMAGE, бросок damageMin..damageMax − defense защитника)`, `MIN_DAMAGE = 1` (константа в коде). Поле `attack` в расчёте пока НЕ участвует. Случайность инжектится через `context.random` (по умолчанию `Math.random`), чтобы функция осталась чистой, а тесты — детерминированными. Заблокированная `MagicImmune` атака подчиняется единому правилу ответки (ответка возможна, если у атакующего нет `NoRetaliation`, защитник жив и это не ответка на ответку) — исключения для блокировки нет. Форма результата: `{ damageDealt, defenderHpAfter, retaliationTriggered, blockedByImmunity, notes }` — отличается от наброска в architecture.md (`{ damageDealt, retaliation, appliedEffects }`); `appliedEffects` появится вместе с эффектами статусов. В `AbilityTag` добавлен `MagicDamage` (различает магические и физические атаки); `AreaAttack` и `Piercing` объявлены, но не реализованы и явно сообщаются через `notes`. Тесты — vitest, 12 кейсов на пары юнитов.
**Причина**: нижний порог `MIN_DAMAGE = 1` не даёт юниту с высокой защитой стать буквально неубиваемым для дешёвых юнитов (это та самая «спираль неуязвимости», которой game-design.md требует избегать — новичок должен оставаться способным «достать» ветерана). Детерминированные тесты на парах юнитов — единственный практичный способ проверить комбинации иммунитетов (architecture.md). Неиспользуемый `attack` — осознанное временное состояние: модель «вычитание защиты» делает защиту абсолютной бронёй, и вопрос, не заменить ли её на HoMM3-подобную процентную (`attack` против `defense`, урон не ниже 30% базового), намеренно оставлен открытым до первой балансной итерации с таблицами юнитов. Единое правило ответки выбрано ради простоты и проверяемости; альтернатива (заблокированная атака ответку не провоцирует) зафиксирована здесь, чтобы выбор был явным, а не случайным. Расхождение формы результата с architecture.md зафиксировано, чтобы наброски в документации не расходились с кодом молча — при появлении эффектов статусов `appliedEffects` либо войдёт в результат, либо architecture.md будет обновлён.

## 012 — Конфиг баланса боя через файл, не через БД
**Решение**: коэффициенты формулы урона (капы атаки/защиты, штраф морали, минимальный урон и т.д.) хранятся в `config/combat-rules.json`, читаются один раз при старте сервера в память и применяются к `resolveAttack`. НЕ в таблице БД. Обязательных полей семь: `attackAdvantagePercentPerPoint`, `attackAdvantageCapPercent`, `defensePenaltyPercentPerPoint`, `defensePenaltyFloorPercent`, `magicResistIsPercentReduction`, `moralePenaltyMultiplier`, `minimumDamage` — минимальный урон тоже вынесен из кода в конфиг (константы `MIN_DAMAGE` в `resolveAttack.ts` больше нет, минимум берётся из `rules.minimumDamage`). Загрузчик проверяет наличие всех полей и их типы и роняет старт с понятным сообщением, если файла нет, он не парсится, не хватает поля или поле неверного типа.
**Причина**: это данные, которые правит только разработчик вручную, редко, не в реальном времени во время игры (цикл "правка вечером → рестарт сервера утром") — файл даёт версионирование через git бесплатно (история правок баланса видна в git log) и не требует подключения инструмента вроде Drizzle Studio для этого конкретного случая. БД остаётся для данных, создаваемых и изменяемых в процессе игры (персонажи, инвентарь, рынок). Аналогичный подход впоследствии, вероятно, будет применён к UnitTemplate/ItemTemplate — решение отложено до момента заполнения контента.

Магический резист сделан процентным снижением, а не двоичной блокировкой (в отличие от оригинала Heroesland) — чтобы убрать резкую "всё-или-ничего" дисперсию результата и сделать магический и физический урон структурно симметричными (оба — процентное снижение, не блок). При этом `MagicImmune` остался отдельным полным блоком для конкретных юнитов с этим тегом: полный блок и частичное сопротивление — разные сущности.

Три мастерства героя (контакт/стрелковое/магия) и снижение брони от физического урона оставлены явными заглушками на 0 — источник (дерево специализаций/предметы/что-то ещё) требует отдельного дизайн-обсуждения, не блокирующего текущий этап. Ненулевое значение заглушки не влияет на расчёт, но попадает в `notes`, чтобы её нельзя было принять за работающий бонус.

## 013 — Сверка с оригинальной формулой HoMM3: пороги защиты, удача, мораль, магический резист
**Решение**: (1) порог защиты возвращён к оригинальным 30% (`defensePenaltyFloorPercent: 30`, то есть множитель не ниже ×0.3), потолок преимущества атаки 400% (×4.0) без изменений; (2) удача — ШАНС срабатывания (`luckChanceByLevel` = 10/25/40% по |luckLevel|, `luckPositiveMultiplier` ×1.5, `luckNegativeMultiplier` ×0.75), а не плавный всегда применяемый множитель; (3) мораль убрана из общей формулы — в оригинале мораль не снижает обычный удар (она либо даёт дополнительный ход, либо пропускает ход, то есть относится к очереди ходов), поэтому в `resolveAttack` остался только специфичный `moraleBonusAttackMultiplier` (0.8) для удара, случившегося БЛАГОДАРЯ дополнительному ходу морали (`isMoraleBonusAttack`); (4) магический резист по процентам удалён из `resolveAttack`, из контекста и из `config/combat-rules.json` — он относится к будущей `resolveSpell`, которой ещё нет (теги `MagicDamage`/`MagicImmune` в `resolveAttack` остаются как упрощённая тестовая абстракция «атака классифицирована как магическая» / «юнит неуязвим к ней»); (5) ответка — полноценный повторный вызов `resolveAttack` со всеми модификаторами (включая удачу отвечающего юнита) и БЕЗ общего понижающего коэффициента; известный будущий случай, пока не реализованный, — ослабленная ближняя атака стрелком при вынужденном ближнем бою (отдельный AbilityTag, например `WeakMeleeRetaliation`).
**Причина**: источник сверки — оригинальная формула Heroes of Might and Magic III, а НЕ Heroesland: у Heroesland порог защиты был смягчён до 80%, из-за чего высокая защита почти не влияла на урон и старые и новые юниты сливались по эффективности. Удача как «шанс × множитель» вместо постоянного множителя повторяет оригинал и даёт редкие заметные всплески и провалы вместо ровного усиления каждого удара. Модель «штраф урона за мораль» была нашим ошибочным предположением: мораль в оригинале относится к системе очереди ходов, а не к формуле урона, поэтому общий штраф удаляем, а специфичный случай (дополнительный ход → ослабленный удар) сохраняем отдельным флагом. Магический резист не имеет отношения к физическому урону, который считает `resolveAttack`; смешивать его с заклинаниями в одной функции значило бы навсегда тащить в боевой движок кусок будущей системы заклинаний, поэтому резист переносится в `resolveSpell`.

## 014 — Бросок урона стека: ограниченное число сэмплов со масштабированием
**Решение**: шаг 3 формулы урона (см. 011) больше не делает один равномерный бросок по диапазону `damageMin × stackCount … damageMax × stackCount`. Вместо этого: `N = stackCount`, `S = damageRollSamples`, `k = min(N, S)`, выполняется `k` независимых целых бросков `damageMin…damageMax` (включительно, как для одного юнита), `scale = N / k`, `stackRoll = сумма × scale`. Округление вниз (`Math.floor`) на этом шаге НЕ делается — оно выполняется один раз в конце (шаг 9), поэтому дробный `stackRoll` допустим и урон не теряется до умножения на множитель атаки/защиты. `damageRollSamples = 10` — обязательное поле `config/combat-rules.json` (целое число ≥ 1, проверяется загрузчиком, см. 012). При стеках до 10 юнитов `k = N` и `scale = 1`, то есть это честный подсчёт без масштабирования. Остальные шаги формулы (flat-бонус, атака/защита, процент-бонус, удача, мораль, минимум урона, применение к пулу HP, ответка) не изменились.
**Причина**: механика совпадает с оригинальной HoMM3 — до 10 юнитов считаем честно, больше 10 берём 10 бросков и масштабируем. Два свойства: (1) нагрузка постоянна и не зависит от размера стека — 10 бросков и для 10, и для 1000 юнитов; (2) относительный разброс НЕ размывается на больших стеках, в отличие от честного подсчёта по каждому юниту. Цифры для обоснования (симуляция по 200 000 ударов на штатном коде проекта в Node): 100 скелетов урона 1–3 — среднее 200 одинаково у всех вариантов, а σ: прежний плоский бросок ≈ 58 (29% от среднего), 5 сэмплов ≈ 37 (18%), 10 сэмплов ≈ 26 (13%), честный бросок на каждого ≈ 8 (4%). 1000 скелетов: 10 сэмплов σ ≈ 258 (13%) против честных ≈ 26 (1,3%). 10 драконов 30–60: прежний бросок σ ≈ 87 (19%), 10 сэмплов σ ≈ 28 (6%). Стоимость шага урона измерена отдельно на том же стеке: ≈ 0,42 мкс на весь вызов `resolveAttack` при стеке из 1000 и 10 сэмплах, то есть ≈ 0,04 мкс на один сэмпл — при таких цифрах постоянство нагрузки на больших стеках не ощущается вовсе.
Рассмотренная альтернатива №1 — оставить прежний плоский бросок (максимальный шум): отвергнуто как слишком случайное для больших стеков, тем более при уже существующем шуме от удачи. Альтернатива №2 — честный бросок на каждого юнита: почти нулевой разброс (σ 1,3% на 1000 юнитов), но нагрузка растёт вместе с размером стека. Число сэмплов вынесено в конфиг, чтобы подстраивать разброс правкой одного числа и рестартом сервера: 5 даёт заметно больший разброс, 3 — ещё больше (чем меньше значение, тем шумнее результат).
Заметка: шаг урона теперь тратит до 10 вызовов `context.random` вместо одного. Детерминизм не пострадал — тесты передают заранее заданную последовательность `random`; удача по-прежнему берёт собственный бросок (`fixedLuckRoll` или `random`) и на шаг урона не влияет.

## 015 — Формула урона: плоский бросок по умолчанию, отдельные множители, одно округление, капы
**Решение** (решения автора, шаг А; полное описание формулы — `docs/combat-formula.md`):
1. **Бросок по умолчанию плоский.** В `config/combat-rules.json` добавлено обязательное поле `damageRollMode` со значением `"uniform"` по умолчанию: один равномерный целочисленный бросок включительно из `damageMin×N … damageMax×N`. Режим `"sampled"` (ограниченное число независимых бросков со масштабированием, запись 014) сохраняется как доступная опция и включается одним полем. Это **меняет режим по умолчанию относительно 014**, но сама запись 014 остаётся в силе как описание режима `sampled` и не переписывается.
2. **Каждый процентный бонус — отдельный множитель.** Навык нападения/стрельбы и `percentDamageBonus` применяются как самостоятельные факторы. В описании разработчика Heroesland бонус за навык прибавляется в одну скобку вместе с разницей атаки и защиты; у нас множитель отдельный, поэтому заявленный процент равен реальному изменению урона.
3. **Округление одно, в самом конце, математическое** — `roundDamage(x) = Math.round(x + 1e-9)` (round half up), экспортируется из `resolveAttack` и покрыта тестами. Промежуточных округлений нет. `minimumDamage` применяется уже после округления.
4. **Капы множителя атаки/защиты сохраняются: ×4.0 (потолок) и ×0.3 (пол).** Прежняя формулировка «+400%» была неточной: правильно «множитель не больше ×4.0, то есть +300%».
5. **Удача и мораль обрезаются до −3..+3** после сложения всех источников (свойства юнита плюс навыки). Раньше уровни удачи выше 3 молча давали шанс 0 вместо обрезки — это исправлено, обрезка фиксируется в `notes`.
**Причина**. (1) Заявленный диапазон урона должен быть честным: если написано «1–3», игрок ожидает увидеть и 1, и 2, и 3, а не «около 2»; плоский равномерный бросок — единственный способ это гарантировать, а `sampled` остаётся настраиваемым для тех, кому нужен другой характер разброса. (2) Причина одна: заявленный процент должен равняться реальному изменению урона. При множителе атака/защита ×2.0 навык +30% при сложении в скобку даст ×2.3, то есть +15% к урону, а при умножении ×1.3 — +30%. (3) Округление вниз систематически «съедало» урон (11.5 → 11), из-за чего заявленные бонусы ощущались слабее; half up — единственное округление, которое не наказывает ровно половину результатов. (4) Капы ×4.0/×0.3 — решение автора. В описании Heroesland указано +5% за очко атаки до +400% и −2.5% за очко защиты «до 80%»; вторая формулировка неоднозначна (пол ×0.8 или снижение до 80%), поэтому мы её не интерпретируем и берём собственные значения. (5) Диапазон ±3 изначально поддерживался только таблицей `luckChanceByLevel` для уровней 1–3, и любое значение вне диапазона молча превращалось в нулевой шанс; явная обрезка с сообщением в `notes` безопаснее и читается как намеренное решение.
Расхождения с описанием Heroesland, зафиксированные намеренно: (а) навык нападения/стрельбы — отдельный множитель, тогда как в описании Heroesland он прибавляется в скобку вместе с разницей атаки и защиты; (б) границы множителя — ×4.0 и ×0.3 вместо «до +400%» и неоднозначного «до 80%»; (в) режим броска выбирается конфигом, по умолчанию плоский. Формулировки написаны своими словами, без копирования справочных описаний Heroesland (репозиторий публичный — см. game-design.md, раздел «Юридическое»).

## 016 — Данные навыков и агрегатор героя
**Решение**:
1. **Навыки — данные.** `config/skills.json` (12 навыков: `offense`, `archery`, `armorer`, `luck`, `leadership`, `tactics`, `sorcery`, `resistance` и четыре школы магии `water_magic`/`air_magic`/`earth_magic`/`fire_magic` без числовых эффектов). Структура навыка: `id` (латиницей), `name` (русское название), `levels` (три русских описания уровней), `effects: [{ target, perLevel: [1, 2, 3] }]`. Допустимые `target`: `meleeOffenseBonusPercent`, `rangedOffenseBonusPercent`, `defensiveArmorReductionPercent`, `luckLevel`, `moraleLevel`, `tacticsRows`, `spellDamagePercent`, `magicResistancePercent`. Загрузчик `server/src/combat/skills.ts` читает файл один раз при старте и валидирует его так же строго, как `combat-rules.json`: неизвестный `target`, неполные `levels`/`perLevel` или битый JSON валят старт с понятным сообщением.
2. **Агрегатор героя — серверная логика.** `server/src/combat/heroModifiers.ts` (не отладка): типы `HeroStats { attack, defense, spellPower, knowledge }` и `HeroLoadout { stats, skills: [{ skillId, level 1..3 }] }` (до 6 навыков, без повторов, понятные ошибки валидации). `aggregateHeroModifiers(loadout, skillsData)` возвращает один объект модификаторов; `applyHeroModifiersToContext(baseContext, attackerMods, defenderMods)` собирает `AttackContext`. Отсутствие героя = все нули.
3. **Ответка решается ролями, а не отдельным блоком.** `AttackContext` и так разделён по ролям: `heroAttackBonus`, навык нападения и удача берутся от героя атакующего, `heroDefenseBonus` и броня — от героя защитника. Ответка — это полный повторный вызов с переставленными ролями, поэтому достаточно поменять местами два объекта модификаторов; отдельный «блок для ответки» в типах не понадобился и не добавлялся. В `AttackContext` добавлено одно необязательное поле `luckBonus` (удача героя складывается с удачей юнита), потому что раньше удача жила только в самом юните и навык героя было некуда положить.
4. **Кап ±3.** Удача и мораль обрезаются до −3..+3 и в агрегаторе, и (защитно) в самом `resolveAttack`; факт обрезки попадает в `notes`.
5. **Что хранится, но не применяется.** `tacticsRows`, `spellDamagePercent`, `magicResistancePercent`, `moraleLevel`, `spellPower`, `knowledge` агрегируются и попадают в `unused` с поясняющей заметкой, чтобы сохранённое число нельзя было принять за работающий бонус. Причины: тактика ждёт поля боя, а магия и знание — будущей `resolveSpell` (см. 013). На `resolveAttack` влияют только `offense`, `archery`, `armorer` и `luck`. `magicOffenseBonusPercent` остался заглушкой в типах: магическое мастерство героя — открытый вопрос дизайна, ненулевое значение только попадает в `notes`.
**Причина**. Ключевой принцип проекта — «данные, а не код» (conventions.md): добавление навыка должно быть добавлением записи в JSON, а не правкой кода. Агрегатор вынесен в `server/src/combat/`, а не в `server/src/debug/`, потому что это боевая логика и она понадобится реальному бою, а не только песочнице. Разделение по ролям выбрано вместо отдельного блока «для ответки» как более простое: у ответки ровно те же бонусы, просто с другой стороны, и лишнее поле в типах со временем стало бы источником ошибок.
